Formula1 solution · proposed architecture · Nov 2026

The backend fetches, the lake shapes, the frontend reads

The backend stops storing F1 data and becomes an ingest app. DuckGraphLake turns what lands into typed views, chart-ready views and a graph. The frontend reads everything from the lake, and a chat agent answers questions through the lake's MCP tools. Two smaller lanes watch the syncing itself: entity CDC on the sync state, and OpenTelemetry from both runtimes. They feed one dashboard in the lake.

The live lane uses a plain REST call to the lake, so the backend needs neither the Business Events module nor a CDC service for F1 data. New files in data/ need a lake restart; overwriting existing ones does not.

CDC, once: the sync state

Entity CDC stays off the F1 data path, but one example is kept to prove the mechanism and because it carries something nothing else does. LiveSyncState is one row that the live sync overwrites every minute. The Mendix database keeps only the latest version, and CDC keeps every one. This is already built and verified (FINDINGS §104, model/backend/27-cdc-stream.mdl).

-- model/backend/27-cdc-stream.mdl (exists)
create or modify change data capture service Formula1Backend.LiveStateCdc
( ServiceName: 'LiveStateCdc' )
{ entity Formula1Backend.LiveSyncState as 'LiveSyncState' (
    RowId as 'RowId', Enabled as 'Enabled', SessionKey as 'SessionKey',
    TelemetryCursor as 'TelemetryCursor', LastRunAt as 'LastRunAt',
    LastResult as 'LastResult', LapsWritten as 'LapsWritten', RunCount as 'RunCount' ); };

# run the backend against the lake's broker; no model change
./mxcli run --local -p Formula1Backend.mpr --runtime-setting Kafka.BootstrapServers=127.0.0.1:9092

The lake builds the rest with no hand-written mapping. The topic is cdc.Formula1Backend.LiveSyncState.1.local. It produces a current-state view and a _history view with change_op and changed_at, an OData entity set Formula1Backend_LiveSyncState, and a SPARQL class of the same name. The dashboard reads the history: when each run happened, what it wrote, and when someone switched the sync on or off.

Metrics from microflows

The lake is an OpenTelemetry receiver. Traces give the duration of every microflow and REST call without changing the model. Metrics activities add the counts that traces cannot show: rows fetched, retries, and events posted to the lake, including in microflows that commit no state. MDL supports all three activities in the current mxcli build.

In the model

-- Sync_Fetch: every OpenF1 request passes here.
-- $Feed is the path up to '?': laps, position, ...
increment counter 'f1.openf1.requests' (Tags: ('feed': $Feed));
increment counter 'f1.openf1.retries'  (Tags: ('feed': $Feed));
increment counter 'f1.openf1.empty'    (Tags: ('feed': $Feed));
increment counter 'f1.openf1.chars' by length($Body)
  (Tags: ('feed': $Feed));

-- Sync_Live: once per run
increment counter 'f1.sync.runs' (Tags: ('result': 'ok'));
increment counter 'f1.sync.laps_written' by $Kept;
set gauge 'f1.sync.rows_fetched' to $Fetched;

At run time

# all of it: scripts/run-backend-on-lake.sh [--mock]
--runtime-setting Kafka.BootstrapServers=127.0.0.1:9092
--runtime-setting 'Metrics.Registries=[{"type":"opentelemetry",
  "settings":{"url":"http://127.0.0.1:4318/v1/metrics","step":"30s"}}]'
--trace-otlp http://127.0.0.1:4318 --trace-service Formula1Backend
OTEL_LOGS_EXPORTER=otlp
# then, after boot, over the admin API:
create_log_subscriber {"type":"opentelemetry", ...}
  • Built and verified. Names arrive unchanged, and the counters match the traces exactly: 53 requests plus 13 retries against 66 HTTP calls.
  • Logs need the exporter and a runtime log subscriber. Studio Pro creates that subscriber from its OpenTelemetry settings; mxcli has no flag for it, so the script adds it after boot.
  • Counters are cumulative and reset when the app restarts. Each dashboard query turns them into increases, and the logic lives in the query because the lake's start-up SQL is fatal when otel.* does not exist yet.

Each lane answers a different question. CDC shows what the sync state was at each run, metrics show how much happened, traces show how long it took, and logs show what went wrong.

Check these before committing

  1. Mendix external entities against the lake's OData. Keys are IRIs and there is one entity set per ontology class. Nobody has yet tried consuming that from Studio Pro, and it decides whether browse pages use OData or SQL.
  2. Concurrent writes and CDC. A CDC event's before and after images both come from the committing microflow's in-memory object, not the stored row. When LiveSyncSet changed the session key during a sync run, the run's event carried the old key in both images. The lake applies after as a whole row, so it showed the wrong value for one cycle (reproduced). The fix is in the lake: apply only the attributes where before ≠ after. The prompts in docs/datalake/prompts/ ask for that fix, and ask Mendix to investigate.
  3. The CDC snapshot rule. The runtime sends a row's existing state only the first time it publishes that revision. A fresh lake folder against an existing database starts the history at the next change, not at the current state.
  4. Where data/ lives outside a dev box. The snapshot lane assumes the backend and the lake share a filesystem. A deployment needs a shared volume, or the snapshot lane moves to events as well.
  5. Where the chat agent runs. MCP listens on loopback, so the tool loop runs in or next to the frontend and only the model call leaves the machine. Set [mcp] allow_changes = false so chat cannot define views.
